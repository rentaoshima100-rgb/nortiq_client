# サイト側の導入手順（エンジニア向け）

Nortiq Revise を新しい案件に入れるとき、**そのサイトのリポジトリに何をするか**。
このファイルだけ渡せば作業できるように書いてある。

Revise 本体（管理画面・API・ウィジェット）は別リポジトリで動いている。
サイト側でやることは、下の4段階のうち**その案件で必要なところまで**。
段階は独立していて、上から順に効果が増える。1段目だけでも運用できる。

| 段階 | やること | かかる時間 | これで何ができるか |
|---|---|---|---|
| 1 | スニペットを1行置く | 5分 | クライアントが本番サイト上でクリックして依頼を出せる |
| 2 | `data-nq-id` を注入する | 30分 | ページを直しても、依頼のピンが正しい要素に付き続ける |
| 3 | ビルド SHA を埋める | 15分 | 「どのビルドに対する依頼か」が確定する。撮影と差分が使える |
| 4 | GitHub App を入れる | 15分 | 画像差し替えの PR が自動で作られる |

---

## 前提: 社内側で先に済ませること

エンジニアが作業する前に、社内が管理画面で案件を登録している必要がある。
登録時に **サイトの URL（オリジン）** と **`snippet_key`** が決まる。この2つを受け取ってから始める。

オリジンは CORS の許可判定に使う。**`https://example.com` と `https://www.example.com` は別物**なので、
本番で実際に配信されている方を正確に伝えること。

---

## 段階1: スニペットを置く（必須）

`</body>` の直前に1行。

```html
<script src="https://nortiq-client.vercel.app/w.js" data-project="＜snippet_key＞" defer></script>
```

### これは本番に常設してよい

**招待トークンを持たない訪問者には一切描画しない。** DOM も作らない。
一般の訪問者にとっては、20KB 弱の JS が1本読まれるだけで何も起きない。

### 確認方法

社内から招待リンクをもらい、そのリンクで本番サイトを開く。
右下にボタンが出れば通っている。出ない場合はコンソールを見る。

| 症状 | 原因 |
|---|---|
| `w.js` が 404 | `src` の URL 違い |
| ネットワークで CORS エラー | 社内に登録されたオリジンと、実際に配信されているオリジンが違う |
| 何も起きない・エラーも無い | トークンが無い（正常）。招待リンクから開き直す |

### CSP を入れている場合

以下を許可する。

```
script-src  https://nortiq-client.vercel.app
connect-src https://nortiq-client.vercel.app
img-src     data: blob:
```

ウィジェットの DOM は closed shadow root の中に閉じている。**サイト側の CSS の影響を受けず、与えもしない。**
`style-src` に `unsafe-inline` が要る点だけ注意（shadow 内に `<style>` を挿す）。

---

## 段階2: `data-nq-id` を注入する

### なぜ必要か

依頼のピンは「ページのどの要素か」を覚えている。何も無いと、**CSS セレクタと文字列**で探すことになる。
ページを直すとセレクタは簡単にずれる。1つ要素を挿しただけで `div:nth-child(3)` は別物を指す。

`data-nq-id` は**ソース上の位置**から作った ID なので、見た目や並びを直しても変わらない。
実測で、指し直しの精度が **確実に当たった 0% → 74%** に上がった。あいまい一致は 43% → 1%。

### 入れ方

`tools/nq-inject/` を Revise 本体からコピーして、リポジトリに置く。

```json
{
  "scripts": {
    "prebuild": "node tools/nq-inject/cli.mjs --root . --out .nq",
    "build": "next build"
  },
  "devDependencies": { "@babel/parser": "^7.26.0" }
}
```

`.gitignore` に `.nq/` を足す。**対応表はコミットしない**（毎ビルドで差分ノイズが出る）。

```sh
node tools/nq-inject/cli.mjs --root . --dry     # 何件付くか確認するだけ
node tools/nq-inject/cli.mjs --root . --out .nq # 実際に書き換える
```

### Babel プラグインでやろうとしないこと

Next.js 15 で実測済み。**両方とも塞がっている。**

- `babel.config.js` を置く → `"next/font" requires SWC although Babel is being used` でビルド失敗
- Turbopack → `Babel is not yet supported` でビルド拒否

ビルド前にソースを書き換えるこの方式なら、Next が動く前に終わっているので普通のソースにしか見えない。
SWC プラグイン（Rust/wasm）を書く必要はない。

### `nq-id` は一意ではない

ループで描画している要素には**同じ ID が複数付く**。これは仕様。
Revise 側は「ID で絞る → テキストか画像の `src` で1つに決める」という順で見ている。
だから、**同じ ID の要素が複数あること自体は問題ではない。**

### ビルドの無いサイト（手書き HTML）

`prebuild` を挟む先が無いので、デプロイのワークフローに1ステップ足す。
GitHub Pages なら `deploy-pages.yml` の build ステップの前。

## 段階3: ビルド SHA を埋める

### なぜ必要か

依頼が「どのビルドに対して出されたか」が分からないと、直したあとに撮り比べても
**直した結果なのか、その間に別の更新が入ったのか**が区別できない。

### 入れ方

`<head>` に meta を1つ。ビルド時に埋める。

```html
<meta name="nq-sha" content="＜commit sha＞">
```

Vercel なら環境変数が来ているので、ビルドスクリプトで差し込むだけ。

```js
// nq-sha.mjs — build の前に走らせる
import fs from 'node:fs';
const sha = process.env.VERCEL_GIT_COMMIT_SHA || 'dev';
const p = 'index.html';
fs.writeFileSync(p, fs.readFileSync(p, 'utf8')
  .replace(/<meta name="nq-sha"[^>]*>/, `<meta name="nq-sha" content="${sha}">`));
```

### Vercel の落とし穴

**Build Command を設定すると、Output Directory を明示しないとビルドが落ちる。**

```
Build Command:    node nq-sha.mjs     （Override ON）
Output Directory: .                   （Override ON）
```

`Output Directory` を空のままにすると `No Output Directory named "public" found` で失敗する。
静的サイトでルートをそのまま配信している場合は `.` を明示すること。

## 段階4: GitHub App を入れる（画像差し替えを使う場合だけ）

クライアントが画像にピンを打って差し替え用の画像を添付すると、**ブランチを切って差し替え、PR を作る**。

### 自動マージはしない。例外なく。

PR が作られるだけ。本番に出るには人間がマージする必要がある。

### 入れ方

社内が用意した GitHub App を、対象リポジトリにインストールする。必要な権限は次の2つだけ。

| 権限 | レベル | 用途 |
|---|---|---|
| Contents | Read and write | ブランチ作成・コミット |
| Pull requests | Read and write | PR 作成 |

インストール後、社内に **リポジトリのオーナー名とリポジトリ名**を伝える。管理画面に登録する。

### 触らせない場所

差し替えが書き込めるのは以下だけ。それ以外は拒否される。

```
許可:  src/  app/  components/  styles/  assets/  public/  index.html
禁止:  package.json  各種ロックファイル  .github/  .env*  *.config.*  tsconfig*.json
```

### 止まる条件

以下のときは何もせず止まる。エンジニアが呼ばれることはない。

- 差し替え画像のアスペクト比が元と 10% 超ずれる
- 添付が元画像の長辺の 70% 未満（引き伸ばすとぼやける）
- 元が SVG
- リポジトリ上のパスを特定できない

---

## 崩してはいけない約束

Revise 側の設計が前提にしていること。**サイト側でこれを壊すと静かに動かなくなる。**

### 1. `<img>` の `src` 属性を消さない

`srcset` だけにして `src` を落とすと、画像の同定ができなくなる。
Revise は `currentSrc` ではなく **`src` 属性**を見ている。`currentSrc` はビューポートで変わるため、
PC で出した依頼をスマホで見ると別の画像を指してしまう。

### 2. Cookie を前提にしない

`/api/w/*` はクロスサイト通信で、**Cookie は載らない**。認証は Authorization ヘッダで通している。
サイト側で Cookie の設定を変えても Revise には影響しないし、逆に Revise が Cookie を要求することもない。

### 3. オリジンを変えたら社内に伝える

独自ドメインを当てた、`www` の有無を変えた、ステージングを増やした。
いずれも CORS の許可判定に直接効く。**変更後は必ず社内に伝えること。** 伝えないと依頼が送れなくなる。

### 4. サイトを作り直したら「設計トークンを取り直す」

参考デザイン案を作るとき、Revise は**そのサイトの CSS から抜いた配色と書体からしか色を選ばない**。
リニューアルしたのに取り直さないと、古い配色で案が出る。社内の案件画面にボタンがある。

## 段階ごとの確認

| 段階 | 確認すること |
|---|---|
| 1 | 招待リンクで開いてボタンが出る／一般の訪問者には何も出ない |
| 2 | `--dry` で何件付くか見る。0 件ならパスの指定が違う |
| 3 | 本番の `<head>` に `nq-sha` が入り、値が `dev` でない |
| 4 | 社内でテスト依頼を1件流し、PR が立つ |

---

## 困ったとき

- **ピンが別のページにも出る** — Revise 側の不具合として直済み。ウィジェットは5分キャッシュされるので、スーパーリロード（Ctrl+Shift+R）で確認すること
- **ピンが少しずれる** — 段階2 が入っていないか、注入対象から漏れている。`--dry` で確認
- **依頼が送れない（CORS）** — オリジンの登録違い。社内に実際の配信オリジンを伝える
- **PR が立たない** — 「止まる条件」のどれかに当たっている。社内の依頼画面に理由が出る
